CRM Workflow API

A small sales workflow API with intentional state changes, optimistic concurrency, and audit trails.

Source code is included in the deliverable bundle. A public GitHub repository has not been created yet.

The problem

What this project addresses

CRM changes are not just CRUD. Stage transitions must be valid, users need to know when their version is stale, and business events should be observable without leaking internal logic into HTTP routes.

Architecture

How the pieces fit together

Token-auth API→Workflow service→State machine→Locked data + audit

Boundaries are deliberately explicit to keep network access, application rules, and persistence separately testable.

Decisions & tradeoffs

What matters in the implementation

  • HTTP and business logic are separated into thin API and workflow layers for independent testing.
  • Deal stage transitions follow a declared state machine, rejecting jumps that bypass business process.
  • Optimistic concurrency uses a version field to prevent silent overwrites of stale deal updates.
  • A file-locked JSON adapter keeps the example runnable without dependencies; a transactional SQL adapter is the production path.

Honest boundaries

What I would change for production

This is a reference API, not deployed multi-tenant CRM software. The one-file store serializes access on one host; production would use MySQL/PostgreSQL, migrations, tenant-scoped authorization, rate limits, queues, and request-level idempotency.
